# 1.0 checks

The three facts [spec-1.0.md](../spec-1.0.md) needed checking before the build. Read from Umbraco's source (`release-17.8.0`) and docs; nothing was run, so the build confirms each with a test.

## Members with Delivery API tokens, and API users

Sources: Umbraco-CMS at tag `release-17.8.0` (paths are relative to `src/`), OpenIddict 7.7.1 and docs.umbraco.com. Nothing was run.

## Fact 1: does `GetCurrentMemberAsync()` see a member who signed in with a Delivery API token?

**Verdict: No, not as our code stands.**

Evidence:
- `Umbraco.Web.Common/Security/MemberManager.cs:152-158, 212-228`: it reads only `HttpContext.User.GetMemberIdentity()`. That is the identity whose `AuthenticationType == IdentityConstants.ApplicationScheme` (`Extensions/MemberClaimsPrincipalExtensions.cs:17`).
- `AddMembersIdentity` uses `services.AddIdentity<…>` (`DependencyInjection/UmbracoBuilder.MembersIdentity.cs`), so the default scheme is the member cookie. A bearer token only ends up in `HttpContext.User` if the endpoint asks for its scheme.
- Umbraco's own Delivery API finds the member in `Umbraco.Cms.Api.Delivery/Services/RequestMemberAccessService.cs:62-83`:
  - It stops unless `MemberAuthorizationIsEnabled()`.
  - It calls `httpContext.AuthenticateAsync(OpenIddictValidationAspNetCoreDefaults.AuthenticationScheme)`. The scheme is `"OpenIddict.Validation.AspNetCore"`.
  - It reads the claims `"umbraco-member-key"` (`Constants.OAuthClaims.MemberKey`) and `"umbraco-member-roles"` (comma-separated).
- The token is made in `Delivery/Controllers/Security/MemberController.cs:203-225`. The principal comes from `MemberSignInManager.CreateUserPrincipalAsync`, with the type `Identity.Application`, and gets both claims. The client-credentials flow for members uses the same code.
- Inferred: once `HttpContext.User` is the token's principal, the member identity is found. OpenIddict's Data Protection token format keeps `AuthenticationType` (`OpenIddictValidationDataProtectionFormatter.cs:69`). Umbraco's `/userinfo` depends on this: it authorizes with the OpenIddict scheme, then calls `GetCurrentMemberAsync()` (`CurrentMemberController.cs:14`, `CurrentMemberClaimsProvider.cs:17`).
- `Api.Common/DependencyInjection/ProcessRequestContextHandler.cs:29-32`: OpenIddict only handles paths that start with `/umbraco/`. Our route qualifies.

What the 1.0 build must do:
- `MemberTargetingContextAccessor` keeps `GetCurrentMemberAsync()` for the member cookie.
- If that finds no member and `DeliveryApiSettings.MemberAuthorizationIsEnabled()`, call `AuthenticateAsync("OpenIddict.Validation.AspNetCore")`.
- Accept the result only if it has `umbraco-member-key`. Backoffice tokens pass the same scheme.
- Then call `memberManager.GetUserAsync(result.Principal)`, which is what `MemberManager.cs:225-226` does.
- Don't put a bare `[Authorize(AuthenticationSchemes=…)]` on the flags endpoint. It would turn away visitors who aren't signed in, and it replaces `HttpContext.User`, which drops the cookie member. If an attribute is used instead, list both schemes plus `[AllowAnonymous]` (unverified).
- Keep the endpoint under `/umbraco/`.

## Fact 2: does an API user pass our permission check?

**Verdict: Yes.**

Evidence:
- Umbraco's own Management API base carries the same policy: `Api.Management/Controllers/ManagementApiControllerBase.cs:26`, `[Authorize(Policy = AuthorizationPolicies.BackOfficeAccess)]`. API users exist to call that API, so they pass this policy by design.
- The policy (`DependencyInjection/BackOfficeAuthPolicyBuilderExtensions.cs:47-51`) uses the OpenIddict validation scheme plus `BackOfficeRequirement`. Its handler (`Security/Authorization/User/BackOfficeHandler.cs:22-37`) checks `IsAuthenticated()` and `CurrentUser.IsApproved`.
- Client credentials (`Controllers/Security/BackOfficeController.cs:314-327, 652-656`) build the principal with `_backOfficeSignInManager.CreateUserPrincipalAsync(user)`, the same as an interactive sign-in.
- `BackofficeSecurity.CurrentUser` (`Web.Common/Security/BackofficeSecurity.cs:27-55`) loads the user by the key in that identity. A search for `UserKind` in Api.Management and Web.Common found it only in models and OpenAPI, never in authorization code.
- Our check is not an authorization handler. It is an MVC `IAuthorizationFilter` (`src/Umbricians.FeatureFlags/Security/FeatureFlagsPermissionAttribute.cs`). It runs after the policy has set the principal and reads `IBackOfficeSecurityAccessor.CurrentUser.Groups[].Permissions`. Nothing in it depends on the kind of user.
- Docs (https://docs.umbraco.com/umbraco-cms/fundamentals/data/users/api-users): an API user is "identical to a regular User" apart from having no password, and is put in user groups.

What the 1.0 build must do: no code change. In docs/api.md, say that the API user needs a user group with the Feature Flags View or Manage permission. Unverified end to end: an integration test with a client-credentials token would settle it.

## Does Umbraco's no-breaking-minors policy cover the backoffice TypeScript API?

**Verdict: Not covered (explicitly, in writing). Partly in practice.** Nothing I could fetch says
`@umbraco-cms/backoffice` is under the policy. The one primary statement on the backoffice
carves it out of the definition of "breaking". Practice shows majors break it freely;
I found no documented minor-release breaks, but I could not prove there are none.

## Evidence
- Policy (C#-framed): "incompatible changes to the 'public API' of Umbraco is considered breaking and
  requires a new major version." and "What exactly the 'public api' is will be determined before the
  final release." https://umbraco.com/blog/moving-to-semantic-versioning/
- Backoffice carve-out, same post: "We will keep the existing definition of what a breaking change is
  for the backoffice for the time being." (the post is old, from the v8 era; I found no later
  statement replacing it).
- Minor releases: "They will not contain breaking changes."; deprecate in a minor, remove in a major.
  https://umbraco.com/products/knowledge-center/versioning-and-release-cadence (page does not mention
  the backoffice).
- Packages: "These are verified to be backwards compatible."
  https://docs.umbraco.com/umbraco-cms/extend-your-project/packages/maintaining-packages (C# context only).
- Breaking-changes page lists only majors: "Breaking changes introduced in each major version"
  https://docs.umbraco.com/umbraco-cms/17.latest/get-started/upgrading-and-migrating/version-specific
- Extension docs (extending-overview) say nothing on stability or what is public.
- npm package.json (main branch, currently 19.1.0-rc): no `@internal`/`@experimental` markers found,
  no description. Root export is null; ~150 subpath exports (`./extension-api`, `./context-api`,
  `./extension-types`...). So "public" = whatever is exported via a subpath, with no tiering.
  https://github.com/umbraco/Umbraco-CMS/blob/main/src/Umbraco.Web.UI.Client/package.json
  (Not checked: CONTRIBUTING.md 404'd at the raw URL I tried; client README has no stability text;
  API Extractor use not found.)

## Breaking backoffice TS changes found (all in majors)
- 17: `@umbraco-cms/backoffice/external/tiptap` removed -> `/tiptap`; current-user exports moved;
  `UmbSectionContext.setManifest()` removed; `ManifestSection` now extends `ManifestElementAndApi`
  instead of `ManifestElement` (a manifest type changed shape).
- 16: context consumption can resolve `undefined` / promise rejects (affects `UmbContextToken` consumers);
  `tryExecute` signature changed.
- 14: UUI renames, icons/localization/property editors moved to extension types.
- 16.0 release notes: "UmbDocumentUrlModel and other models not exported to npm package" (export gaps
  fixed after release). https://our.umbraco.com/download/releases/1600
- Minor-release breaks: none documented in the pages above; absence is not a guarantee.

## What is public
No official definition for the client. Practical reading: anything importable from a published
`@umbraco-cms/backoffice/*` subpath, but the project does not promise it is stable across minors.

## Implications for a package promising aliases, entity types, a manifest type and a context token
- Do not cite Umbraco's policy as covering these; it only covers what your package itself exposes.
- Your own aliases and entity-type strings are plain strings you control: stable by your own promise.
- Your manifest type and `UmbContextToken` are your exports but built on Umbraco types
  (`ManifestWorkspaceView`, `UmbContextToken`, condition maps): promise them per Umbraco major only
  and state that explicitly (e.g. "stable within a major; we follow Umbraco majors").
- Peer-range `@umbraco-cms/backoffice` (and NuGet Umbraco.Cms) to one major; add a CI build/typecheck
  against each new minor/RC to catch silent breaks early.
